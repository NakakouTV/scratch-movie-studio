# 動画生成方式の改善（2026-09-26）

公式Scratchを操作し、その画面を収録する方針を維持して、録画エンジンと区間の結合処理を変更しました。1920×1080、30fps、H.264/AACのMP4、途中保存・再開、場面別動画に対応します。

## 実装した流れ

1. ChromeのscreencastでJPEGとキャプチャ時刻を受信します。音声開始と同じブラウザの時刻を基準にします。時刻が欠ける場合のみ受信時刻へフォールバックし、その回数を記録します。
2. 30fpsの時刻ごとに直前の画像を選び、FFmpegの標準入力へ渡して録画中にH.264へ圧縮します。静止中も画像を必要な枚数だけ繰り返します。JPEGファイルは作りません。入力の書き込み完了を待ち、待機中の画像が64MiBを超えた場合は明示的なエラーにします。
3. Scratchの音声出力をMediaRecorderで収録します。ゼロ値の音声源を収録先だけにつなぎ、Scratchが無音でも先頭の無音時間が欠落しないようにします。新しい効果音を鳴らす処理ではありません。
4. 区間の長さを整数の映像フレーム数で確定します。音声は48kHz・ステレオで1フレームあたり1600サンプルに切りそろえ、不足分を無音で補います。結合用の音声をFLACで保持し、単独再生できるMP4も保存します。
5. 新方式の区間同士を結合する場合、映像は再圧縮せずコピーします。正確な区間長を指定し、AACの開始遅延が映像時刻へ入り込まないようにします。音声はFLACから連結してAACへ変換します。全体動画と場面別動画に同じ方法を使います。

正常生成後の区間に残るファイルは `movie.mp4`、`audio.flac`、`recording.json` です。中間動画・Opus音声は正常生成後に削除します。旧方式で既に生成されたJPEG画像には手を加えません。録画失敗時の未確定区間は完成動画に含めず、診断用に残します。

旧方式の保存区間が混在する場合は、従来の30fpsでの再エンコード処理に切り替えます。旧方式の途中保存を新方式だけの結合と誤認しないよう、バージョン・映像プロファイル・フレーム数・音声サンプル数を判定します。

## 検証

- `node tests/recording-stream.mjs`：異なる長さの3区間で発音と画面の点滅を収録。結合後102フレームの全時刻が30fpsの格子に一致し、全フレームの復号後の画素が結合前と一致。発音と画面変化のずれは、この環境で約67ms（2フレーム）。旧方式との混在、中断、録画中のエンコーダー終了、FFmpegがない場合、音声エンジンがない場合も合格。
- `node tests/checkpoint-resume.mjs --record --scenes`：PEN作品30操作。素材追加直後の停止、保存データの復元、ブロック追加直後の意図的な失敗、再開が合格。9区間・50.5秒の全体動画と5本の場面別MP4を生成。失敗区間の混入・重複なし。音声・映像を全デコードし、完成プログラムと素材も一致。
- `node tests/drag-tracking.mjs`：4回の追加・上下左右の遠距離ドラッグ。ポインターとつかみ位置の追従、ドラッグ中のスクロール、MP4出力が合格。

|項目|以前の方式|新方式|
|---|---:|---:|

|JPEG画像と画像一覧の新規保存量|約96.2MB|0MB|
|完成MP4|約1.69MB|約1.55MB|
|結合用のFLAC音声|なし|約11KB（無音の例）|

旧測定では別のChromeテストも並行していました。新方式では録画中と `stop()` の完了までにも映像を圧縮しているため、最後の0.34秒を全圧縮時間と解釈することはできません。総所要時間の厳密な速度比較ではなく、中間画像をなくしたことと終了後の処理量を確認する測定です。

## 残る制約

録画は実時間です。30fps出力でも、PCの負荷やブラウザの描画遅延で取得できなかった動きを復元することはできません。上記の音声同期値はこの検証条件の実測であり、すべての環境での上限ではありません。FLACはOpus収録後の音声を追加劣化なく保持するもので、元のScratch音声を最初から無圧縮で収録する方式ではありません。

録画中にもFFmpegのCPU負荷がかかります。長時間・高負荷作品については引き続き実際の映像で確認が必要です。途中再開に必要なMP4・FLAC・メタデータは保持してください。
